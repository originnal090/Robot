# 单次动作与完成回执（STEP_V1）

间歇自主模式默认对搜索转向、对齐转向和可选横移执行一次完整动作组，等待完成回执，
再经过 `settle_seconds` 稳定画面，重新识别。前进仍使用原来的远近速度与间歇窗口。
`slow_realtime` 和手动连续控制保持原来的向量接口。

## 启用

PC 与机器人端都需要本次代码。机器人端仍是独立文件
`robot_side/tonypi_server.py`，无需安装新的第三方库，也不需要修改或训练识别模型。
替换机器人实际运行的这个文件并重启对应服务；PC 重启 GUI。部署位置和操作见
`deploy/TONYPI_CUTOVER.md`。本次实现没有远程部署或驱动真机运动。

```toml
[controller]
approach_mode = "normal_then_slow"
single_step_turns = true
step_timeout_seconds = 10.0
settle_seconds = 0.4
```

服务连接后发送 `CAPS:STEP_V1`。硬件模式只有存在
`Board.setBusServoPulse` 时才声明支持；dry-run 也支持协议，但只模拟完成。
PC 单步模式下若未收到能力声明，在第一次需要转向时停止自主并报
`step_protocol_unavailable`，不会偷偷降级为持续转向。

旧课程服务可显式设置 `single_step_turns = false`，恢复之前的定时窗口行为。
`config.unity.toml` 已关闭单步，因为当前 Unity 服务没有这个回执协议。
Fanout 的完成状态只取自主机器人主连接。新版 Unity 镜像会接收独立的 `MIRROR_STEP:`
开始、心跳和终态事件，在动作开始时连续播放有限步幅，真机完成时结束同步。
这部分是可调的刚体动作预览，不是实测姿态。镜像异步发送，不阻塞真机心跳；
旧 Unity 会忽略这类事件。详情见 [Unity 协议](../unity/PROTOCOL.md)。

## 线协议

每条消息以换行结束，与原有 JSONL、`CMD:`、`DIST:` 共用连接。
STEP 使用独立前缀，旧服务会忽略它，不会解析成持续运动向量。

```text
机器人 → PC: CAPS:STEP_V1
PC → 机器人: STEP:{"id":"4a267d","steer":0.35,"lateral":0.0}
机器人 → PC: STEP_STATUS:{"id":"4a267d","status":"accepted","detail":""}
PC → 机器人: STEP_PING:4a267d
机器人 → PC: STEP_STATUS:{"id":"4a267d","status":"done","detail":""}
```

`id` 为 1–64 位字母、数字、下划线或短横线，PC 实现使用随机 UUID。
`steer` / `lateral` 恰有一个非零，必须是有限的 [-1, 1] 数值且越过服务端死区。
不接受速度、抓取或任意动作文件路径。实际动作组仍由服务配置里的方向/档位映射决定。

状态包括：

| 状态 | 含义 |
| --- | --- |
| `accepted` | 请求已接收，等待或正在执行；不表示执行完成 |
| `done` | 这一动作组所有帧均已下发，并等待了每帧的设定时长 |
| `cancelled` | 取消、断线或心跳过期，剩余帧不再下发 |
| `error` | 非法请求、忙碌、动作文件或硬件错误等，原因在 `detail` |

同一连接同一 ID 不会执行第二次，重复请求只返回已保存状态，改变载荷也不会改变原请求。
每个连接最多保存 1024 个 ID，满后拒绝新 ID 而不淘汰旧记录，防止淘汰后重发导致再次执行。
忙碌或非法请求的 ID 同样保留，不能在之后用同一 ID 重新启动动作。
断线后 PC 不自动重连重发动作；新连接是新的会话，不能把跨连接重试当作幂等操作。

## 执行、取消与故障

厂商 `runActionGroup` 会捕获并打印部分异常，`runAction` 对缺文件或忙碌状态可能直接返回，
所以不能简单地在调用返回后无条件发送成功回执。
单步执行器采用厂商相同的 `.d6a` SQLite 动作数据及 `Board.setBusServoPulse` 接口：
先只读加载并校验整组帧，再逐帧下发一次。不会进入服务原先的持续动作循环。
所有动作继续共用同一把执行锁，避免与手动动作并发写舵机。

动作文件限定在 `/home/pi/TonyPi/ActionGroups`，完整校验帧时长、舵机脉宽、非空内容与
最长 30 秒总时长。缺文件、数据损坏或执行接口异常不会报告 `done`；
执行失败会发送 `error` 并锁定服务故障，要求修复后重启。

PC 等待时约每 0.2 秒发送独立心跳。服务端在帧边界检查 1.5 秒心跳期限。
STOP、其他旧接口控制命令及连接断开都会取消待执行/执行中的 STEP。
已经下发给舵机的当前帧仍等待到设定时间结束；不发送后续帧，然后回报取消。
这不是立即断电或硬件急停，最长取消响应时间受当前动作帧时长限制。
取消不代表已回到站立姿态，不能把取消状态当作完成对齐。

PC 在等待完成时不重复发运动向量、不进行视觉决策。正常 `done` 到达后才开始稳定计时；
操作员或避障主动中断时等待取消结束后重新稳定观察。意外取消、执行错误或超时会停止自主，
发送 STOP，且不自动重发动作。视频失效仍保留原有停止保护。

`done` 只证明动作序列执行流程结束，不包含实际转角、落脚成功、舵机到位或机器人平衡反馈。
如果最小动作组仍转过整个对齐区，仍需要标定小步动作、对齐容差或近距离横移策略。

课程包动作文件的只读检查结果：左转小步 1350 ms、右转小步 1450 ms，普通左右转各
1000 ms，左右小横移分别为 1000 / 1100 ms，单帧最长 300 ms，均通过执行器格式校验。
这说明“小步”不等于“更短播放时间”；实际安装的动作文件可能不同，以机器人文件为准。

## 验证方式

`tests/test_single_step.py` 通过真实 TCP 连接运行服务与 PC 客户端，舵机接口使用记录桩，
覆盖单次执行、完成时序、重发、忙碌、取消、断线、心跳、坏文件、硬件异常和状态解析。
`tests/test_step_runtime.py` 验证控制循环在超过旧脉冲窗口后仍等待完成、完成后再稳定、
回执超时不重试、解除自主不误报失败，以及旧服务的显式兼容模式。
这些测试不代表真机角度精度或平衡能力已经验证。
本轮控制、TCP、机器人服务、GUI、手柄和采集回归共 292 项通过、1 项跳过。
